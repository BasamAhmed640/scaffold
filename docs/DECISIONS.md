## Learner model (LM-05 … LM-09)

| ID | Decision | Reason |
|---|---|---|
| D-06 | "Unassisted correct attempt" in the status rules means correct, unassisted **and confidence ≥ 2**. A guess (confidence 1) is logged but is evidence for no status, not only for mastery. | LM-06 says a guess is not mastery evidence; letting a guess move a KC from `unseen` to `fragile` would contradict "knows what he knows". |
| D-08 | FSRS rating map extensions: `partial` → Hard, `unanswered` → Again. Concept memory starts at the first `taught` event or first evidence-correct answer, so failed pretest answers before teaching create no memory. FSRS runs without fuzz and without short-term (minute) steps. | LM-08 maps only correct/incorrect. Determinism is needed for rebuild equality (ARC-08); concept checks are day-scale. |
| D-09 | An "I don't know" at least 3 days after the last success counts toward `forgotten`, like an incorrect answer. It never opens a misconception and is excluded from calibration. | Failing to retrieve is forgetting; LM-07 only forbids treating it as a wrong guess. |
| D-14 | "The anchor Anki card lapsed since the last sync" is read as: a lapse on the anchor card later than the KC's last evidence-correct concept check. | Makes `forgotten` clear itself after the next successful check instead of sticking until another sync. |
| D-15 | Misconceptions: an exhibit is an incorrect or partial answer citing the misconception id. A new exhibit while open restarts the resolution count. A correct answer "targets" a misconception when the attempt names it or its bank question lists it in `misconception_targets`. Resolution needs ≥ 2 distinct questions and two such answers in different sessions ≥ 20 h apart. Any exhibit after resolution reopens it. Low-confidence single errors with a stated belief are kept as `candidate` so the grader can reuse the id. | Fills in the LM-05 wording precisely enough to test. |
| D-25 | `needs_check` is set by an Anki lapse, leech or stale flag on a linked card, a `card_flagged` event, or reopening the subject; it is cleared by the next attempt on that KC. It applies only to KCs that were learned (status fragile/solid/forgotten) for planning. | LM-09 sets the flag but does not say how it clears. |

## Visual engine (M7: VIS-01 … VIS-05)

| ID | Decision | Reason |
|---|---|---|
| D-68 | The theme shim (`src/core/visuals/theme.ts` → `visual-kit/theme.css`) is built from the inline visualizer's documented design system: surface, text and border variables; the short aliases `--p --s --t --bg2 --b`; role tokens; `.t .ts .th .box .node .arr .leader .sr-only`; and nine `c-<ramp>` ramps of 7 stops each. Ramp fill/stroke/title/subtitle use stops 50/600/800/600 in light mode and 800/200/100/200 in dark. Dark mode follows `prefers-color-scheme`, and `data-mode="light"` or `data-mode="dark"` on the root forces a mode. Every `var()` in a shim rule carries a fallback. **Deviation:** VIS-04 says to build the list by inspecting saved widgets, and none exist on this PC yet. The manual V-VIS check (ENVIRONMENT.md, manual check 3) compares a real Claude Desktop widget and adds whatever differs. | No saved widgets to inspect; the documented system is the same source the widgets are generated from. |
| D-69 | `register_visual` returns one of three statuses. `accepted` means the visual is stored. `needs_fix` means nothing was stored and one fix attempt is allowed. `dropped` means it was still unusable after the fix. The fix attempt is the second registration of the same `visual_id` in the same session (or on the same local day outside a session). That second call is final: it is accepted, with warnings if needed, or dropped when the problem is fatal (malformed markup, over the size limit, a root that is not `<svg>`, network references). A third registration in that window is refused with `fix_limit`. A failed update of an accepted visual leaves the stored version in place. In a later session a visual can be updated again. | VIS-05: "one automated fix attempt, after which the visual is accepted with warnings or dropped. It never loops (ARC-10)". |
| D-70 | `visual_registered` gains `session_id`, `status`, `attempt` and `source_sha256`. Defaults keep older events valid. The figure source is not in the event log (it can be 600 kB): figures are vault content, like question notes, and the hash lets checks detect hand edits. `rebuild --restore-missing` therefore cannot recreate a deleted figure; the visual must be registered again. | Keeps events.jsonl small; ARC-08 still rebuilds the registry itself (tested). |
| D-71 | `spec.md` is written whole on registration, because registering is an explicit content action, like `add_question` creating its note. Afterwards the render check changes only the derived `checks` key and the `figure` marker region (LM-02). The note also gets an "Alt text" section. Generator code goes in a fence longer than any backtick run inside it. | VIS-03 lists purpose, KC links, what to notice, alt text, and generator code or provenance. |
| D-72 | Concept notes list only accepted visuals. An SVG visual is embedded (`![[…/figure.svg]]`). An HTML visual embeds `preview.png` once the render check has written it, and always links `[[…/index.html\|Open the interactive version]]`; Obsidian opens that in the default browser. | VIS-03; avoids a broken embed before the first render check. |
| D-73 | The static checks parse SVG as XML and HTML tolerantly (void elements, optional end tags). They require a non-empty `<title>` as a direct child of the root `<svg>` or an `aria-label`. HTML needs a `<title>`, an `aria-label` or a `.sr-only` summary. A missing `<desc>` or `viewBox` is only a warning. An explicit font size under 11 px is an error, whether it comes from an attribute, an inline style or a px size in a `<style>` block. Network references cover URL attributes, `srcset`, CSS `url()`/`@import`, and script `fetch`/`import`; `data:` URIs and `#fragments` are allowed. The shim is injected only when the source uses its classes or `var(--…)`. | VIS-05 fast checks; IF-04. |
| D-74 | The render check runs SVG inline in a page 680 px wide, the way it sits in a note (height comes from the viewBox), and runs HTML as its own page at a 680 px viewport. The page is served in-process from a reserved `.invalid` origin; every other request is aborted and reported. Light and dark mode use emulated `prefers-color-scheme` in separate contexts, and each problem is tagged when it occurs in only one mode. **Text boxes:** SVG `<text>` elements and HTML text-node line boxes. The ink box is the font box trimmed 20 % at the top, 10 % at the bottom and 1 px at each side. **Errors:** ink boxes of different texts overlap by more than 1 px in both directions; text lies outside the viewBox or viewport (1 px tolerance); the effective font size (computed size × screen scale) is under 11 px; an HTML page is wider than the viewport. **Plot fidelity:** for each `[data-scaffold-plot]` curve, 50 points spaced by arc length are inverted in screen space and compared with the spec's equation; an error over 1 % of the y range fails. Contrast under WCAG AA is a warning (V-UI). Each step has a 15 s timeout and there are no retries. The browser is the bundled Chromium, with the installed Edge channel as the single fallback (REL-04). | VIS-05 and V-VIS give the checks but not how to compute them. |
| D-75 | The plot template uses its own recursive-descent expression evaluator. It accepts numbers, the x variable, `params`, `pi`/`e`, `+ − * / ^` and a whitelist of Math functions, and looks names up as own properties only, never `eval`. Curves default to 240 samples. Labels sit directly beside each curve in a right gutter sized to the longest label (at most 30 characters); there is no legend. Axis labels carry the unit when one is given. The spec JSON is the generator. | VIS-02: computed curves, saved generator, labels next to what they name, units. |
| D-76 | Visual kinds are `diagram`, `stepper`, `mechanism`, `plot`, `widget`, `comparison` and `dashboard`. CLI behaviour: `visual add` reads a file or a `--plot` spec. `visual check --file` checks files outside the vault (for example the README hero) and writes `<name>.preview.png` next to them. `visual open` uses the platform's default app (`explorer.exe` on Windows); `SCAFFOLD_NO_OPEN=1` only prints the path, and tests set it. `visual plot` writes a computed SVG. | D8 row "Visuals"; the README hero must pass `scaffold visual check` (C6). |
| D-77 | The render tests skip when no browser can start, unless `SCAFFOLD_REQUIRE_RENDER=1`; CI will set it after `npx playwright install chromium` (M9). ## Question quality and grading audits (M8: QB-03, QB-04, V-QQ, V-GRADE)

| ID | Decision | Reason |
|---|---|---|
| D-81 | **V-GRADE sampling.** `scaffold grade sample` draws up to 40 tutor-graded answers, split evenly across model families. It takes only free-text and visual answers (mc and numeric are graded by code), excludes `unanswered`, and skips answers that were already audited or are on an unscored sheet. | D-82 | **V-GRADE scoring.** `scaffold grade score` reports Cohen's κ over {correct, partial, incorrect} per provider family and overall, with confusion matrices. Recall of confident-wrong answers = among answers the owner labelled incorrect with confidence ≥ 3, the share the tutor also graded incorrect. A partial grade on such an answer does not count as caught. The audit passes when κ ≥ 0.70 for every family present and recall ≥ 0.90; with no confident-wrong answers in the sample, recall is "not measured" and the audit does not pass. Each scored sheet is appended once to `audits/history.jsonl`, and drift is the change in κ since the previous audit. `--apply` records the owner's label as `grade_overridden` (by `owner`) wherever it differs; it is never automatic. | The spec gives the thresholds but not the recall definition; the strict reading is the useful one for misconception tracking. |
| D-83 | **V-QQ.** `scaffold q audit` checks what was actually served: every bank question used in an attempt must pass lint now (QB-03) and must have had an `ok` verdict at the time of the attempt (QB-04, replayed from the event log). `scaffold q spotcheck` writes the monthly sheet of 10 `ok` questions, putting already-answered ones first.
